01 · 第一章

两座仓库：GitHub 与 Gitee 的分工

代码只存在自己硬盘上，等于船坞里的库存：硬盘会坏、目录会删错、改乱了的文件回不到上周三。托管仓库做的事很具体——把你的提交历史原样复制到另一台服务器上。问题是复制到哪台。

⚓ 1.1两台服务器，两种性格

GitHub 是全球开源生态的事实中枢：几乎所有重要的开源项目都托管于此，CI（Actions）、静态站点（Pages）、包仓库（Packages）、代码审查围绕它长成了一整片体系。它还有一层身份——一份能点开的简历。代价是它在墙的另一侧：连通性按时刻波动，故障时要靠 githubstatus.com 区分「我的问题」和「它的问题」。

Gitee（码云）是开源中国团队的国内托管平台：服务器在国内，clone、push 不用碰运气；免费私有仓库政策大方，适合放不能公开的工作代码。它的性格也更「守规矩」——实名认证制，想公开一个仓库要过人工审核。

先回答「两个都用是不是太麻烦」：不麻烦，这是笔成本几乎为零的保险。git 的 remote 机制天生支持多个远端地址（第四章实操），一份提交 push 两次就是两份异地副本。真正的分工是：GitHub 当门面被人看，Gitee 当备份保下限——哪天 GitHub 连不上，Gitee 那份随时能开工。

⚓ 1.2注册台上的三件小事

① GitHub 的两步验证（2FA）绕不过去——2023 年底起对活跃用户强制开启。装一个验证器 App（Aegis、1Password 都行），扫一次码，并把恢复码抄在纸上：手机丢了，恢复码是唯一的后门。

② Gitee 的实名认证早做早好。要用 Pages（虽已下线）、要开开源仓都绕不开它，人工审核高峰期可能要等几天——别等到发布当天才想起来。

③ 用户名就是门牌号。GitHub 用户名会出现在每个仓库 URL、每页 Pages（github.com/你的名/仓库名）、甚至提交统计里。取一个五年后还愿意署在封面上的名字，改名的成本随提交数上升。

02 · 第二章

认证：密码已死，令牌与钥匙对

账号是身份证，认证是每次 push 都要重考的门票。GitHub 与 Gitee 都只认两种凭证：HTTP(S) 通道的令牌，SSH 通道的密钥对。它们的原理、管辖和坑各不相同。

⚓ 2.1密码是怎么死的

2021 年 8 月 13 日起，GitHub 彻底关闭了「账号密码推代码」——密码只在网页登录时有用。原因很直接：密码一旦在别处泄露（撞库、钓鱼），攻击者能直接重放它对代码仓库做任何事；而令牌可以限定权限、限定仓库、设定过期时间，泄露的伤害被圈在授权范围内。Gitee 的 HTTPS 通道同样不再接受账号密码，逻辑相同。

GitHub 现在发两种令牌：老的 classic token（前缀 ghp_，权限按「作用域」整片授权，比如勾了 repo 就等于全部仓库读写）；新推荐的 fine-grained token（前缀 github_pat_）可以只勾选某几个仓库、只放行 Contents 读或写、必须设过期日。同一件事，伤害半径差一个量级——发令牌时多点的每一下勾选，都是将来泄露时的损失边界。

好消息是你不需要背令牌。git 的凭证协议分两步：git credential fill 在推送前向凭证助手（credential helper）要凭据，没有就弹一次登录框；成功后 git credential approve 把它交给助手存储。Windows 的 Git 自带 Git Credential Manager，背后是系统凭据管理器；macOS 用钥匙串。于是「第一次弹窗、之后免输」，令牌躺在系统保险箱里自动出示。

⚓ 2.2SSH：私钥不出门的挑战-应答

SSH 认证的核心是一对钥匙：私钥住在本机 ~/.ssh，永远不联网；公钥贴上平台，谁都能看——它推不出私钥。push 时港口发来一串随机数（挑战），本机用私钥签名回递，港口用公钥验证。秘密本身从未上线，抓包也抓不走能重放的东西。

算法选 Ed25519（EdDSA，256 位）：密钥串比 RSA 短得多、签名更快，安全性相当；只有在伺候特别老的系统时才需要退回 RSA（4096 位起步）。三行配好：

git-bash
$ ssh-keygen -t ed25519 -C "you@example.com"   # 生成密钥对，落在 ~/.ssh
$ cat ~/.ssh/id_ed25519.pub                    # 复制这行「公钥」
$ ssh -T git@github.com                        # 第一次会问是否信任主机指纹，yes

公钥分别贴到 GitHub 的 Settings → SSH and GPG keys 和 Gitee 的 设置 → SSH 公钥。一把钥匙可以同时开两台服务器，不用各配一套。验证成功的原话长这样：

真实输出
Hi StarrySea1412! You've successfully authenticated, but GitHub does not provide shell access.

第一次连接时那个「是否信任主机指纹」的提问值得认真对待——确认的是 known_hosts 里的服务器指纹，防的是中间人冒充平台。

⚓ 2.3经典追问：HTTPS 还是 SSH？

两个都合法，区别在运维面。HTTPS 走 443 端口——互联网上最不可能被封的端口；凭证交给凭据管理器，换机时重新授权一次即可；令牌撤销与重发都在网页上完成。SSH 免去了令牌管理，配一次用到天荒地老，还能用 deploy key 给 CI 发一把只读钥匙；但默认走 22 端口，部分网络环境对它不友好——备用方案是 GitHub 官方的 443 航道，写进 ~/.ssh/config：

~/.ssh/config
Host github.com
  HostName ssh.github.com
  Port 443
  User git
本篇的裁决：个人日常用 HTTPS + 凭据管理器（少管一把钥匙）；多台机器、CI、以及 22 端口被封的环境用 SSH；Gitee 私有仓直接上 SSH——它的 HTTPS 凭证通道对第三方工具不算省心，SSH 一次通过后从未再折腾。

提交：三区流水线与对象库

git 把目录划成几个舱室：工作区是你正在改的文件，git add 把选中的内容写进暂存区（这批提交的装箱单），git commit 把整箱内容拍成一张快照存进本地对象库，git push 才把快照复制到远程服务器。

⚓ 3.1提交的是什么：快照，不是文件

很多人把 commit 想成「存了几个文件」，实际存的是三样东西：blob（文件内容的字节）、tree（目录结构，把 blob 和文件名对上）、commit（指向一个 tree，记录父提交、作者、时间与说明）。每样东西都有一个 SHA-1 哈希——40 位十六进制，内容变一位，哈希就面目全非。所以 git 的历史本质是「一串快照」，而非「文件修改记录」：回滚、分支、diff，全都是在快照之间做算术。

这也解释了 commit message 该写什么——既然快照记下了「改了什么」，message 的任务是「为什么」。修复 HUD 暗色模式对比度 有信息量，改了点东西 没有。惯例是祈使句、首行 50 字符内（详情挪空行之后的正文，72 字符换行）——git 自家的提交历史就是按这个格式写的。

⚓ 3.2对象库解剖：.git 里到底存了什么

commit 的老家是 .git/objects。打开看，里面是 256 个两字符命名的抽屉（00/ 到 ff/）——对象 SHA-1 的前两位当抽屉名、后 38 位当文件名。每个对象在磁盘上的原样结构是「类型 + 空格 + 字节数 + NUL + 内容」：一个 10 字节的 hello git 文件入库时，blob 的完整原文是 blob 10\0hello git\n——对这一整段算 SHA-1，得到的就是它的身份证号。tree 和 commit 同理，只是内容换成目录清单和提交元数据。

三条对象规则决定了 git 的一切脾气：①内容寻址——对象名就是内容的哈希，改一个字节，名字面目全非，所以历史改不动也赖不掉；②同内容即同对象——两个文件字节相同就共享同一个 blob，改了十版都没动过的 LICENSE 全程只存一份；③对象只增不改——新快照产生新对象，旧对象永不覆写（git gc 会把散对象打包成 packfile 压体积，但内容语义不变）。

经典追问：SHA-1 都被 Google 攻破过（2017 年 SHAttered，碰撞成本约 263），git 为什么还敢用？那场攻击是「预谋构造」——攻击者事先花 months 算出两份长得一样哈希不同的 PDF。git 面对的威胁完全不同：攻击者要在改一个字后让新内容恰好撞上 40 位十六进制的既有对象，概率 2-160，且 git 自 2017 年起内置了碰撞检测（sha1dc），收到伪造对象会当场拒收。工程上「换哈希」的成本（所有对象改名、所有引用迁移）远大于「加检测」——所以 SHA-1 至今稳坐，SHA-256 仓库作为备选格式已在路上。

⚓ 3.3首航全流程

git-bash · 新仓库的第一次推送
$ git init                          # 项目根目录起本地仓库（生成 .git/）
$ git add .                         # 全部装上暂存区（先确认 .gitignore！）
$ git commit -m "first commit"      # 快照入库，得到首个 SHA
$ git branch -M main                # 主分支命名 main（GitHub 新仓默认）
$ git remote add origin git@github.com:you/repo.git
$ git push -u origin main           # -u 记住上游，此后 push/pull 不必再指名

之后的日常只剩三拍：add → commit → push。暂存区存在的意义是允许分批：同一个文件改了两处，git add -p 可以只把其中一处装进这次提交——把「一次提交 = 一个说得清的动作」变成物理上可能的事。

⚓ 3.4开船前先写 .gitignore

不是所有文件都该进库：密钥与令牌（.env、*.key）——push 只要一秒，撤干净要重写全部历史（每个老快照里它都还在）；依赖目录（node_modules/、venv/）体积巨大，且能靠 lock 文件复原；构建产物（dist/、__pycache__/）随时可再生。库里只收藏「源」。

经典追问：为什么 .gitignore 对已跟踪的文件无效？因为 ignore 规则只作用于「还未被跟踪」文件的枚举阶段——已被 add 过的文件在索引里有正式户口，状态检查根本不会去对照 ignore 名单。解法是先撤销户口再补规则：git rm --cached 秘密.env（从索引删除、保留工作区文件），提交后 ignore 才开始管它。顺序反了等于白写。

⚓ 3.5后悔药：reset 三档与 reflog

提交错了、改砸了，是 git 使用者的日常。后悔药有两瓶：git reset 拆提交，git revert 反着再提交一份。reset 有三档，差异全在「动哪几个区」——这是新手事故率最高的一条命令：

命令（起点：HEAD 已提交 v2，暂存区有 v3）HEAD暂存区工作区后果
git reset --soft HEAD~1→ v1不动不动v2 的改动整体退回暂存区，换个说法重提
git reset --mixed HEAD~1（默认档）→ v1重置为 v1不动改动退回工作区变成未暂存，重新挑选
git reset --hard HEAD~1→ v1重置为 v1重置为 v1未提交的 v3 改动当场蒸发——慎用

经典追问：--hard 之后，数据真丢了吗？分两种。已经 add 过的内容：blob 早已写进 .git/objects，reset 只是让引用不再指向它——git fsck --lost-found 能把悬空对象捞回来，git gc 默认对可达性过期对象留 2 周、松散对象 30～90 天（gc.reflogExpire 90 天 / gc.reflogExpireUnreachable 30 天）才真正清理。从没 add 过的：只存在于工作区的字节，git 从没见过它——真没了。一句话，git 只会丢「你从没让它记过的东西」。所以事故现场的第一反应不是慌，是 git reflog：HEAD 的每一次移动（reset、checkout、rebase）都有登机记录，git reset --hard HEAD@{2} 就能回到任何一站。

还要立一条纪律：reset 改写历史，只许对没 push 过的提交用。push 之后的分支上，改写等于把历史抽走一节——协作者那边的分支跟它分叉，谁也合不上。公共分支上的后悔药是 git revert：不改历史，加一个「反向提交」把坏改动抵消掉，历史完整，人人能对账。

04 · 第四章

双仓：一条 remote，两台服务器

把同一个仓库推到两台服务器，是最便宜的异地容灾：GitHub 那份给别人看，Gitee 那份保下限。做法有懒与勤两种，坑也各有一个。

⚓ 4.1懒办法：Gitee 导入仓库

Gitee 新建仓库页有「导入已有仓库」：填入 GitHub 仓库地址，它连提交历史一起搬过来；仓库页上有「强制同步」按钮，点一下从 GitHub 拉齐一次。适合「本地为主、偶尔备份」——但它不会自动同步，忘点是常态。

⚓ 4.2勤办法：给 origin 挂两条 push 地址

git-bash
$ git remote set-url --add --push origin git@github.com:you/repo.git
$ git remote set-url --add --push origin git@gitee.com:you/repo.git
$ git remote -v
origin  git@github.com:you/repo.git (fetch)
origin  git@github.com:you/repo.git (push)
origin  git@gitee.com:you/repo.git (push)      # ← 一次 push，逐条推送

两个必须说透的细节。其一：一旦手动追加过 push 地址，fetch 就只认第一个 URL——想从 Gitee 拉，另开一条 git remote add gitee git@gitee.com:you/repo.git，平时 git fetch gitee。其二：多条 push 地址是串行执行的——第一条（GitHub）卡 20 秒超时，第二条（Gitee）也得干等；任何一条失败，这条 push 命令整体报错。所以「断网时双推还能救 Gitee」是错觉——要推 Gitee，就单独 git push gitee main。互动 05 的断网开关，复现的就是这件事。

⚓ 4.3经典追问：双仓会自动同步吗？

不会。push 是人发起的动作，Gitee 导入仓的「强制同步」也是按钮不是定时器。真要自动，办法有两个：GitHub Actions 里跑一个镜像工作流（每次 push 到 main 后追加推送到 Gitee，用 secrets 存密钥），或者干脆维持「本地一次 push、两台服务器各收一份」的手动纪律。个人项目用后者足够——自动化的复杂度应该买在刀刃上。

还要立一条纪律：两台服务器永远来自同一台本机的历史。两台机器各推一台服务器，两边历史就分叉了——remote 各看各的，谁也合并不了谁，得手动对账。多机器协作时，先定哪台是主服务器。

🧭 真实走查 · 二
一个双仓仓库的 .git/config 原文

本机一个图形仓库的实盘配置——GitHub 公开、Gitee 备份，两条 pushurl 并列：

.git/config（节选）
[remote "origin"]
    url = git@github.com:starrysea1412/machine-skill-cg125.git
    fetch = +refs/heads/*:refs/remotes/origin/*
    pushurl = git@github.com:starrysea1412/machine-skill-cg125.git
    pushurl = git@gitee.com:starrysea1412/machine-skill-cg125.git

push 一次两台各收一份；release 大附件走 GitHub，国内读者 clone 走 Gitee。第四章的全部知识就是这几行 config。

05 · 第五章

断网：超时、代理、镜像与 API 兜底

在国内推 GitHub，Failed to connect to github.com port 443: Timed out 不是事故，是天气。这一章不抱怨天气，只发救生装备——但装备要按顺序用，先隔离变量，再对症下药。

⚓ 5.1第一步永远是隔离变量

排查不是玄学，是把问题切成两半：

git-bash
$ curl -I --max-time 8 https://github.com        # 通 → 大概率不是墙，查代理配置
$ curl -I --max-time 8 https://gitee.com         # 通 → 本机无罪，是 GitHub 航路的事

三个结论三条路：两个都通 → 问题在你自己的 git 配置（多半是代理残留）；GitHub 不通、Gitee 通 → 本机网络无罪，按下面的药箱顺序来；两个都不通 → 先修自己的网。

⚓ 5.2代理是双向坑

本机挂着代理（比如 127.0.0.1:7890）时，git 不会自己用——要显式交代，而且建议用 socks5h 而不是 socks5：多个 h 表示域名解析也交给代理做，绕开本地 DNS 污染：

git-bash
$ git config --global http.proxy socks5h://127.0.0.1:7890
$ git config --global --unset http.proxy          # 代理软件一关就摘掉

反过来是更常见的病：代理软件已经关了，全局配置里的代理却没摘，git 还在虔诚地敲一扇不存在的门——表现为一切 fetch/push 卡几十秒后超时。诊法就藏在报错里：看到 Failed to connect to 127.0.0.1 port 7890，就是 git 在找本地代理。本篇发布当晚就撞上一次，解法不改全局配置，单次覆盖：

当晚的真实命令
fatal: unable to access 'https://github.com/.../': Failed to connect to 127.0.0.1 port 7890
$ git -c http.proxy= -c https.proxy= push -u origin main   # 本次推送绕过代理，一次通过

⚓ 5.3镜像加速与它的保质期

对 release 附件、raw 文件的下载，社区反代是特效药——在原链接前加前缀：https://ghfast.top/https://github.com/...。但公共镜像有保质期：曾经满地的 ghproxy.com、ghp.ci 都已阵亡，活着的节点也常对大仓库 clone 半路断流。别把镜像写死进脚本，当成人肉可换的消耗品；真要稳定，用自建反代（开源项目 hunshcn/gh-proxy 可部署到 Cloudflare Workers）。

⚓ 5.4终极兜底：Git Data API 五步空投

HTTP API 与 git 的智能协议走的是不同端点，墙对它们的待遇可能不同——当晚 github.com 的 git 端点死了，api.github.com 却活着。只要 API 可达，就能把文件直接写进仓库，不走 git 协议。五步：

REST API · 逐一发射
# ① 建三份 blob（文件内容的 base64）
POST /repos/:owner/:repo/git/blobs   {"content":"…","encoding":"base64"} → 得 3 个 sha
# ② 取旧 tree，替换其中 3 个条目，建新 tree
GET  /repos/:owner/:repo/git/trees/main?recursive=1
POST /repos/:owner/:repo/git/trees   {"base_tree":…,"tree":[{新 path+sha}…]}
# ③ 建 commit：指向新 tree，父提交是旧 commit
POST /repos/:owner/:repo/git/commits {"message":"…","tree":…,"parents":[旧 sha]}
# ④ 把 main 指向新 commit —— 效果等同 push
PATCH /repos/:owner/:repo/git/refs/heads/main {"sha":新 commit}
# ⑤ 网页刷新 —— Pages 自动重建，线上已更新
🧭 真实走查 · 三
比五步本身更值钱的两个坑

当晚五步一次走通，倒是在细节上翻了两跤，都值得记进本篇：其一，curl 的 JSON 带中文时必须写成文件再 -d @body.json——命令行内联中文经 Windows shell 转码就烂，报错还看不出是编码问题；其二，token 放请求头 Authorization: Bearer <token>，别拼进 URL——URL 会进 shell 历史和服务器日志。这套五步在自动发版场景同样能打，不只是救急。

⚓ 5.5先看官方是不是着火了

还有一类「连不上」根本不是你的问题：平台自己故障。发布前一切失败，先花十秒开 githubstatus.com——某次发布撞上 Pages 官方事件，排查了半天自己的仓库，最后发现是灯塔自己着火了。看一眼状态页，省一小时怀疑人生。

发布：GitHub Pages 与它的规矩

仓库不只是货架，还能直接变成网站。GitHub Pages 把仓库里的静态文件发布成 github.io 上的正式页面——你此刻读的这篇 VOL.14，就住在那里。

⚓ 6.1三种发布源，三种摆法

仓库 Settings → Pages 选发布源，保存后一两分钟，https://你的名.github.io/仓库名/ 就挂灯了。三个选项对应三种摆法：main / 根目录——仓库根就是网站根，文章站、文档站最常用；main / docs 目录——代码和网页分家，docs/ 才是店面；gh-pages 分支——给构建产物住的单间，Actions 构建完把成品推到这条分支，源码与成品各安各的。

两个容易被忽略的机制：其一，Pages 默认会对站点跑一遍 Jekyll 处理，以下划线开头的文件会被吞——纯静态站放一个空的 .nojekyll 文件跳过它；其二，项目站发布在 /仓库名/ 子路径下，资源引用要用相对路径，写死了绝对路径的 CSS/JS 在本地能跑、线上 404。

免费额度是软限但要知道：站点 1GB、月带宽 100GB、每小时构建 10 次。正规文档站都远摸不到；被限流了再考虑加 CDN。

gh-pages 半成品：404 的两种打开方式

协作：Issue、分支、PR 与五人的边界

一个人用仓库是自言自语；第二个人上船，就需要旗语——Issue 说事，分支干活，Pull Request 合流。

⚓ 7.1Issue：把「不对劲」说成「能修的事」

好的 Issue 不是「坏了！」，是三段论：怎么操作（复现步骤，编号列出）、期望什么、实际发生什么，附上版本号、截图、报错原文。写得好的 Issue 一半是修好了的——它逼提的人把变量隔离清楚，看的人直接拿到起点。自己给自己提 Issue 也有价值：待办从脑子里搬进仓库，带着上下文躺在代码旁边。

⚓ 7.2分支与 PR：主干永远能跑

团队节奏的默认值：主干 main 永远可用；任何改动开一条短命分支（feat/hud-console、fix/login-timeout），改完发 Pull Request（GitLab 叫 MR，GitLab 之外都叫 PR，是同一件事）——「请求把这条分支并回主干」。合并前有人看一眼（review），CI 跑一遍测试，绿了才合。经典追问：fork 和 clone 差在哪？clone 是把仓库复制到本地，归属不变；fork 是在服务端复制一份到你名下——你拥有这份拷贝的写权限，改完向原仓库发 PR。给别人的项目贡献代码，走 fork 流；在公司仓库里干活，直接开分支（你有那台仓库的权限）。

给开源项目提 PR 的礼数：先读 CONTRIBUTING.md（没有就照着最近合并的 PR 依样画葫芦），一个 PR 只做一件事，改动说明里贴 before/after。公开仓库可以免费配分支保护（要求 review、要求 CI 通过才能合）——给主干上的 main 上一道闸。

⚓ 7.3PR 的生命周期：一道闸门的完整流程

一个 PR 从开到合走五站：open（分支已推、PR 已建，CI 开始跑）→ review（三种表态：Approve 放行、Request changes 打回改、Comment 只留言不挡道）→ CI 绿（自动化测试通过）→ merge（三种合法：merge commit 保留分叉史、squash 压成一个提交、rebase 拉直贴上去）→ delete branch（分支用完即弃，主干永远整洁）。任何一站红掉，PR 就停在原地等改——这不是官僚流程，是把「主干永远能跑」翻译成机器可执行的规则。

机器可执行的开关叫分支保护（Settings → Branches）：勾上 Require a pull request before merging、要求至少 1 个 approve、要求 status check 通过、禁止 force push——之后任何人（包括仓库主人）都绕不过 review 直接 push main。经典追问：为什么不让大家直接 push main，非要多一道闸？因为主干是全队的下游：一个没跑过测试的红提交混进 main，所有人的 pull 都带着它，CI 全红、发布冻结，排查成本是全队的时间；而闸门的成本只是 reviewer 一次点击。事故概率 × 事故代价，远大于每次点击的成本——这道闸是 git 协作里性价比最高的一笔交易。冲突也不会因为闸门消失：两人改了同一行，后合的 PR 会标 conflict，解法永远是「把 main 拉进自己的分支（merge 或 rebase），手工裁决同一行，重新 push」。

决定开源时补两块板：LICENSE——不写许可证等于「保留所有权利」，别人连 fork 都不敢；MIT 最宽松，Apache-2.0 带专利条款，都只需原样贴进文件。 README——首页即门面：一句话是什么、截图或在线地址、三行上手。私有仓库也请放 README——三个月后的你就是第一位读者。

速查卡：如果只带走十二句

贴在手边的那一页。每句都是前面七章的浓缩，展开版见各章。

① 密码推不了代码——命令行只认令牌（HTTPS）或密钥对（SSH），GitHub 2021 年 8 月就关了密码通道。
② HTTPS 交给凭据管理器，SSH 私钥不出门——二选一都能走通，22 端口被封就写 ~/.ssh/config 走 443。
③ add 是装箱单，commit 是快照，push 才出门——三区别混，一次提交说清一件事。
④ .gitignore 只防新文件——已入库的要先 git rm --cached，顺序反了白写。
⑤ 双仓是给 origin 追加 pushurl——多条地址串行执行，一台断网会拖住整条命令；推 Gitee 就单独 push gitee。
⑥ fetch 只是把远端对象拉回来对账，pull 才会动你的工作区——先 fetch 后合并，永远比裸 pull 稳。
⑦ 报错先读最后一行，再隔离变量：同一个网 curl 两个域名，一秒分清「墙」和「自己」。
⑧ 代理是双向坑：没挂上会超时，忘摘掉也超时——报错里出现 127.0.0.1 就是后一种。
⑨ Pages 404 按序查四步：官方状态页 → push 完没 → 构建绿没 → 强刷缓存。
⑩ 重要数据 3 份、2 种介质、1 份异地——双仓就是成本最低的那份异地。
⑪ commit 存的是三层对象：blob 内容、tree 目录、commit 快照——内容变一位 SHA-1 全变，历史赖不掉也改不动。
⑫ reset --hard 不是坟场——add 过的 blob 还在对象库里，reflog 90 天内都捞得回；公共分支后悔用 revert，别改写历史。

收尾：三份副本，两种介质，一个异地

数据安全的 3-2-1 法则：重要数据存 3 份，放 2 种介质，其中 1 份在异地。git 把这个法则拆成了最朴素的形态——本地仓库是一份，任何远程是第二份，双仓是第三份；磁盘是一种介质，云端是另一种；GitHub 与 Gitee，总有一个在「异地」。
