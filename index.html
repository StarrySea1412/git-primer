第 1 港

开港之前：先想清楚代码住在哪

一艘船停在船坞里，不叫航运，叫库存。写完只存在自己硬盘上的代码也一样——硬盘会坏，目录会删错，改乱了的文件再也回不到上周三。托管仓库这件事，本质是给船找一个出了你的地盘也能靠泊的港。

⚓ 1.1两座港口，两种性格

GitHub 是全球开源世界的中央车站：几乎所有重要的开源项目都停在这里，文档、CI、包管理、代码审查围绕它长成了一整片生态。对开发者来说它还有一层身份——一份能点开的简历。代价是：它在墙的另一侧，连通性要看时刻和运气。

Gitee（码云）是国内访问最稳的托管平台：服务器在国内，clone、push 都不用碰运气；免费私有仓库政策大方，适合放不能公开的工作代码和个人备份。它的性格也更「守规矩」：想公开一个仓库，得先实名认证，再等人工审核。

结论先给：这不是二选一的题。它们是分工——GitHub 当家门面，Gitee 当保险柜。门面负责被人看见，保险柜负责在你最倒霉的那天让你还能开工。第 4 港会手把手把两个港接成一条航线。

⚓ 1.2注册台上的三件小事

两边的账号注册都不难，值得写下来的只有三件：

① GitHub 的两步验证（2FA）现在绕不过去——2023 年底起对活跃用户强制开启。装一个验证器 App（如 Aegis、1Password），扫一次码，把恢复码抄在纸上。这十分钟的保险，将来救的是整个账号。

② Gitee 的实名认证早做早好。要用 Pages、要开开源仓都绕不开它，而人工审核高峰期可能要等上几天——别等到要发布那天才想起来。

③ 用户名就是你的门牌号。GitHub 的用户名会出现在每一个仓库 URL、每一页 Pages 里（github.com/你的名/仓库名），取一个愿意五年后还署在封面上的名字。

· · · 航段 1 · · ·
第 2 港

第一次握手：HTTPS 还是 SSH

账号是身份证，认证是船票。每次 push，港口都要验一次「这条推送真的是你发的吗」。验法有两种，性格完全不同——HTTPS 像出示证件，SSH 像对暗号。

⚓ 2.1HTTPS：出示证件

HTTPS 认证就是用户名 + 令牌。注意，是令牌不是密码——GitHub 从 2021 年 8 月起彻底停掉了「密码推代码」，密码只能在网页登录时用。命令行里要的是 Personal Access Token：在 Settings → Developer settings → Tokens 里生成，现在推荐 fine-grained 类型——可以只授权某几个仓库、只给读写 Contents 的权限、设定过期日。令牌泄露的伤害范围，取决于你给它的权限有多大。

好消息是你不需要背下这串令牌。Windows 的 Git 自带凭据管理器（Credential Manager）：第一次 push 弹出登录窗口，授权一次，之后它替你把令牌收进系统保险箱，每次自动出示。macOS 用钥匙串，Linux 可配 libsecret。

⚓ 2.2SSH：对暗号

SSH 认证的核心是一对钥匙：私钥住在你电脑里，永远不出门；公钥贴到平台上，谁都能看，但它推不出私钥。push 时，港口发来一道随机的「暗号题」，你的电脑用私钥签了名递回去，港口用公钥验证——答案本身从头到尾没有传输过，所以抓包也抓不走任何能重放的东西。

配一对钥匙只要三行：

git-bash
$ ssh-keygen -t ed25519 -C "you@example.com"   # 一路回车，钥匙对落在本机 ~/.ssh
$ cat ~/.ssh/id_ed25519.pub                    # 复制这一整行「公钥」
$ ssh -T git@github.com                        # 验船票：Hi StarrySea1412! 就通了

公钥分别贴到 GitHub 的 Settings → SSH and GPG keys 和 Gitee 的 设置 → SSH 公钥。一把钥匙可以同时开两个港，不用各配一套。

墙内还有一步先手棋：SSH 默认走 22 端口，有些网络环境对它不友好，但 443 端口（HTTPS 用的那个）通常畅通。GitHub 官方在 ssh.github.com:443 留了一条备用航道，写进 ~/.ssh/config 即可：

~/.ssh/config
Host github.com
  HostName ssh.github.com
  Port 443
  User git

🧭 真实走查 · 一
Gitee 那次「Authentication failed」

某天给一个私有仓推 Gitee，HTTPS 通道稳定报 Authentication failed——凭据管理器里存的 GitHub 令牌被 Gitee 拒收，Gitee 的 HTTPS 密码通道又早不支持。换 SSH 后一次通过，改动只有一行：

git-bash
$ git remote -v
origin  https://gitee.com/starrysea1412/video-agent-lab.git (fetch)
$ git remote set-url origin git@gitee.com:starrysea1412/video-agent-lab.git
$ git push   # 枚举对象 → 写入 → 通了，从此没再折腾过

经验收进航海日志：Gitee 私有仓，直接上 SSH，别在 HTTPS 上浪费时间。

· · · 航段 2 · · ·
第 3 港

代码上船：add、commit、push 的三区流水线

git 把你的目录划成几个舱室：你正在改的文件在工作区，git add 把选中的货搬上暂存区（这批货的装箱单），git commit 把整箱封舱、钉上一个永不重复的编号，存进本地仓库；而 git push 才让船真正离港，驶向远程。

⚓ 3.1首航全流程

git-bash · 新仓库的第一次出港
$ git init                          # 在项目根目录起一个本地仓库（.git 舱）
$ git add .                         # 全部装上暂存区（先确认 .gitignore 写好了！）
$ git commit -m "first voyage"     # 封舱，形成第一个提交
$ git branch -M main                # 主分支命名为 main
$ git remote add origin git@github.com:you/repo.git
$ git push -u origin main           # -u 记住航线：以后 push/pull 不用再指名

之后的日子就只剩三拍：add → commit → push。一天的活儿可以摊成十个小提交，也可以攒成一个大提交——但每个提交都应该是一个能说明白的完整动作，像「修复 HUD 面板在暗色模式下的对比度」，而不是「改了点东西」。

⚓ 3.2开船前，先写 .gitignore

不是所有货都该上船：密钥和令牌（.env、*.key）绝不能进仓库——推上去只要一秒，撤干净要脱一层皮（历史里每个提交都还留着它）；依赖目录（node_modules/、venv/）体积巨大且能用 lock 文件复原；构建产物（dist/、__pycache__/）同理。仓库只收藏「源」，不收藏「随时能再生成的零件」。

尤其提醒：.gitignore 只对还没被跟踪的文件生效。已经 add 过的文件，要先 git rm --cached 秘密.env 再补 ignore——顺序反了等于白写。

· · · 航段 3 · · ·
第 4 港

双港记：一条船，两个港

把同一个仓库推到两座港口，听起来奢侈，其实是最低成本的保险：GitHub 那份给别人看，Gitee 那份给自己留后路。哪天一家抽风，另一家随时接管。

⚓ 4.1偷懒方案：Gitee 一键导入

Gitee 新建仓库页有一把「导入已有仓库」的钥匙：填入 GitHub 仓库地址，它会连提交历史一起搬过来，之后仓库页上还有「强制同步」按钮，点一下就从 GitHub 拉齐一次。适合「本地为主、偶尔备份」的节奏——只是它不会自动同步，忘点是常态。

⚓ 4.2正经方案：一条 remote，两条推送航线

更顺手的是让 git push 一次推两港。给 origin 追加一条推送地址：

git-bash
$ git remote set-url --add --push origin git@github.com:you/repo.git
$ git remote set-url --add --push origin git@gitee.com:you/repo.git
$ git remote -v
origin  git@github.com:you/repo.git (fetch)
origin  git@github.com:you/repo.git (push)
origin  git@gitee.com:you/repo.git (push)      # ← 一次 push，两港靠泊

两个细节记牢：其一，一旦追加过 push 地址，fetch 就只认第一个 URL——想从 Gitee 拉，另开一条：git remote add gitee git@gitee.com:you/repo.git，平时 git fetch gitee。其二，双推是「镜像」不是「同步」——两个港的历史永远来自同一条船，别在两台机器上各推一港，否则历史分叉，比单港还乱。团队协作出多台机器时，先想清楚哪边是主港。

🧭 真实走查 · 二
machine-skill-cg125 的双仓 .git/config

本机一个图形仓库就是这么双修的——GitHub 公开、Gitee 备份，.git/config 里如实记录着这条双航线：

.git/config（节选）
[remote "origin"]
    url = git@github.com:starrysea1412/machine-skill-cg125.git
    fetch = +refs/heads/*:refs/remotes/origin/*
    pushurl = git@github.com:starrysea1412/machine-skill-cg125.git
    pushurl = git@gitee.com:starrysea1412/machine-skill-cg125.git

push 一次，两港各收一份；release 大附件走 GitHub，国内读者 clone 走 Gitee。这份 config 就是第 4 港的全部秘密。

· · · 航段 4 · · ·
第 5 港

风浪与灯塔：断网、超时与自救

在国内用 GitHub，push 卡死不是事故，是天气。Failed to connect to github.com port 443: Timed out 这种报错，每个双仓水手都背得出来。这一港不抱怨天气，只发救生衣。

⚓ 5.1先分清：是墙，还是自己船漏了

排查的第一步永远是把变量隔离开：

git-bash
$ curl -I --max-time 8 https://github.com        # 通 → 大概率不是墙，查代理配置
$ curl -I --max-time 8 https://gitee.com         # 通 → 你本机没问题，就是 GitHub 航线的事

若 Gitee 通而 GitHub 超时，本机无罪，按下面的药箱顺序抓药。

⚓ 5.2救生衣四件

① 代理。本机挂着代理（比如 127.0.0.1:7890）时，git 不一定自己会用它——要显式交代：

git-bash
$ git config --global http.proxy socks5h://127.0.0.1:7890
$ git config --global --unset http.proxy          # 代理软件一关，记得撤掉，不然-fetch 也会卡死

最坑的是反过来：代理软件已经关了，全局配置里的代理却没撤，git 还在虔诚地敲一扇不存在的门——表现为所有 fetch/push 卡死几十秒后超时。这两种病症状一样，病因相反，先看 git config --global --get http.proxy 再下药。

② 镜像加速。对 release 附件、raw 文件的下载，社区反代是特效药——在原链接前加前缀：https://ghfast.top/https://github.com/...。但公共镜像像浮标，会漂也会沉：曾经满海的 ghproxy.com、ghp.ci 都已经阵亡。别把它们写死进脚本，当成人肉可换的消耗品。clone 整仓它们帮不上，老老实实走代理或镜像仓库。

③ SSH 走 443。第 2 港那纸 ~/.ssh/config，在 22 端口被封的网络里就是通行证。

④ 终极兜底：Git Data API。只要 HTTPS API 还能通（它走的路径和网页相同），就能把文件直接「空投」进仓库——不走 git 协议。它是五步：建 blob（文件内容）→ 建 tree（目录结构）→ 建 commit（把 tree 钉进历史）→ 把分支 ref 指向新 commit → 完事。第 5 走查里逐层拆给你看。

🧭 真实走查 · 三
push 被墙的那一夜：Git Data API 五步空投

某晚《你按下回车之后》要更新线上版本，push 死活超时（curl 56 Recv failure），代理也不在。当晚的绕航路线——用 GitHub REST API 把改动的文件直接写进仓库：

五步空投 · curl 逐一发射
# ① 建三份 blob（新文件的 base64 内容）
POST /repos/:owner/:repo/git/blobs   {"content":"…","encoding":"base64"} → 得 3 个 sha
# ② 取旧 tree，替换其中 3 个条目
GET  /repos/:owner/:repo/git/trees/main?recursive=1
POST /repos/:owner/:repo/git/trees   {"base_tree":…,"tree":[{新 path+sha}…]}
# ③ 建 commit，指向新 tree 和旧 commit
POST /repos/:owner/:repo/git/commits {"message":"v3.5 via API","tree":…,"parents":[旧 sha]}
# ④ 把 main 指向新 commit —— 效果等同 push
PATCH /repos/:owner/:repo/git/refs/heads/main {"sha":新 commit}
# ⑤ 网页刷新 —— Pages 自动重建，线上已更新

两个当晚踩过的坑，比五步本身更值钱：curl 的 JSON 里带中文时必须写成文件再 -d @body.json——命令行内联中文经 Windows shell 转码就烂；token 用请求头 Authorization: Bearer <token>，别塞进 URL。这套五步在无人机自动发版场景里同样能打，不只是救急。

⚓ 5.3灯塔：先看官方是不是着火了

还有一类「连不上」根本不是你的问题：GitHub 自己故障。发布前一切失败，先花十秒开 githubstatus.com——某次发布撞上 Pages 官方事件，排查了半天自己的仓库，最后发现是灯塔自己着火了。看一眼状态页，能省下一小时怀疑人生。

· · · 航段 5 · · ·
第 6 港

把家开成店面：Pages 发布

仓库不只是货架，还能直接变成店面。GitHub Pages 把仓库里的静态文件发布成网站——你此刻读的这篇文章，就是住在 github.io 上的。

⚓ 6.1三步开张

仓库 Settings → Pages，选一个发布源，保存。三个选项对应三种摆法：

main 分支 / 根目录——最常见，仓库根就是网站根，适合文章站、文档站；main 分支 / docs 目录——代码和网页分家，docs/ 才是店面；gh-pages 分支——给构建产物住的单间，Actions 构建完把成品推到这条分支，源码和成品各安各的。保存后一两分钟，https://你的名.github.io/仓库名/ 就挂出灯了。

三个免费规矩要背下来：只服务静态文件（没有后端，接口自己去别处搭）；仓库超过 1GB 或站点带宽超限会被限流；正式项目记得在页面上留 noindex 之外的家底——LICENSE 和 README。

🧭 真实走查 · 四
gh-pages 半成品：404 的两种打开方式

某次发布一个多页站点，push 还在进行中就顺手点了开启 Pages，构建抢跑，成品缺了一半——线上首页 404。排障半小时，结论只有两行：先确认 push 彻底完成（对象计数、远端进度都走完），再开 Pages；开了之后等构建状态变绿（仓库 Actions 页能看到那次 Pages build 的日志），刷新才有意义。

加上走查三末尾那条——先查 githubstatus.com——发布失败的排查顺序就齐了：状态页 → push 是否完成 → 构建是否绿 → 缓存（强刷 Ctrl+F5）。四步走完还不好，再来怀疑人生。

· · · 航段 6 · · ·
第 7 港

信号旗与瞭望台：协作的规矩

一个人用仓库，像自言自语地航海；一旦有第二个人上船，就需要信号旗语——Issue 说事，分支干活，Pull Request 合流。

⚓ 7.1Issue：把「不对劲」说成「能修的事」

好的 Issue 不是「坏了！」，而是三段论：怎么操作（复现步骤）、期望什么、实际发生什么。附上版本号、截图、报错原文。写得好的 Issue 一半是修好了的——因为它逼提的人把变量隔离清楚，而看的人直接拿到起点。

⚓ 7.2分支与 PR：主干永远能跑

团队协作的默认节奏：主干 main 永远保持可用；任何改动开一条短命分支（feat/hud-console、fix/login-timeout），改完发 Pull Request（Gitee 里叫 PR，GitLab 叫 MR，说的是同一件事）——「请求把这条分支并回主干」。合并前有人看一眼（review），有机器人跑一遍测试，绿了才合。个人项目同样值得这么做：PR 是给自己的一次慢下来的机会，改动在分支上摆开，比在主干上裸奔体面得多。

贡献别人的项目则是 fork 流：把仓库 fork 到自己名下 → clone 自己那份 → 开分支修 → 推回自己名下 → 向原仓库发 PR。你的改动通过审核后，就永远留在了那艘大船的航海日志里。

归航：三份副本，两种介质，一个港外

数据安全的 3-2-1 法则：重要数据存 3 份，放 2 种介质，其中 1 份在异地。git 把这个法则拆成了最朴素的形态——本地仓库是一份，任何远程是第二份，双仓是第三份；磁盘是一种介质，云端是另一种；Gitee 或 GitHub，总有一个在「异地」。

这套指南本身也是航海日志的一部分：你现在读到的页面，住在一个双仓仓库里，刚刚完成它自己的第 14 次航线复用——add、commit、push，两港靠泊，Pages 挂灯。代码的家安好了，剩下的，是天天出航。
